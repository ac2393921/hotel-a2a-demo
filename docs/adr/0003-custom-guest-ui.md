# ADR 0003: 専用ゲストUIの構成

- Status: Accepted
- Date: 2026-10-07

## Context

MVPのゲスト体験では、会話履歴とFront Deskの変更提案を同じ画面で確認し、ゲストが明示的に承認または拒否できる必要がある。ADK付属の開発UIは開発・デバッグには便利だが、承認状態やホテル向けの会話体験を示す専用UIには向かない。

各部署Agentは独立したA2Aサービスとして継続する。ブラウザーから部署Agentへ直接アクセスさせず、Front Desk Agentが既存の振り分けとA2A連携を担う。デモの会話状態はプロセス内メモリに置く。

## Decision

- FastAPIでローカル向けのゲストUI APIと静的ファイル配信を提供する。
- ブラウザー画面はHTML、CSS、JavaScriptで構成し、外部フォントや外部スクリプトに依存しない。
- APIはADK `Runner` と `InMemorySessionService` を使い、すべてのゲスト発話をFront Desk Agentへ渡す。
- 会話履歴とRestaurantの保留中提案をUIへ返す。提案は明示的な承認後にFront Deskが確定処理を行い、承認前に予約が変更済みと表示しない。
- 公開する会話テキストはゲストとFront Deskのものに限る。部署Agentの内部処理、推論、プロンプト、メモリはUI APIから公開しない。
- APIと静的UIは既存の一括起動スクリプトに加え、`127.0.0.1`だけにバインドする。

## Consequences

- ゲストは専用画面で会話し、変更案の状態を見て承認・拒否できる。
- 追加のJavaScriptフレームワークや永続DBを導入せず、ローカルデモの起動を簡潔に保てる。
- 会話はサーバープロセス再起動で失われる。複数利用者や永続履歴は対象外。
- ADK Webは引き続き開発者のAgent検証に使えるが、通常のゲスト向け起動先は専用UIとなる。

## Alternatives considered

- **ADK Webをゲスト画面として使う:** 起動は簡単だが、提案承認の状態やホテル固有の画面を制御しづらいため採用しない。
- **ブラウザーから各部署Agentを直接呼ぶ:** A2Aの独立サービス境界とFront Deskの調整責任を崩すため採用しない。
- **フロントエンド用フレームワークを追加する:** MVP画面の規模に対して依存とビルド工程が増えるため、現時点では採用しない。
