# ADR 0005: Restaurant予約業務の拡充とヘキサゴナルアーキテクチャ

- 状態: 承認済み（下記の未決事項を除く）
- 決定日: 2026-10-07
- 関連: ADR 0002、ADR 0004
- 置き換える判断: ADR 0002のRestaurantに関する「19時から20時への固定変更」の業務範囲を拡張する。Hub-Spoke、公開A2A境界、承認前に確定しない原則は維持する。
- 対応Epic: [#45](https://github.com/ac2393921/hotel-a2a-demo/issues/45)
- 実装状態: 未実装。現行Restaurantの公開契約は実装完了まで変更されない。

## 背景

ゲストが館内1店舗について日時・人数・席の条件を相談し、空席と代替案から予約を決める体験へ拡充する。現行実装は単一予約の固定時刻変更と保存・検証が一体であり、業務の拡張には責務の分離が必要となる。

## 決定

### 構成と責務

- Restaurant予約業務のAPIをヘキサゴナルアーキテクチャで構成する。初期段階は同一Restaurantサービス内のPython APIとし、別HTTPサーバーを必須にしない。
- ドメインは営業時間、利用時間、人数、席種、重複判定を所有し、ADK・A2A・LLM・保存実装に依存しない。
- アプリケーション層は空席検索、予約照合、新規提案、変更提案、提案確定を提供する。
- 入力アダプターはRestaurantの業務toolとA2A受付。toolの候補名はsearch_availability、find_reservations、propose_reservation、propose_reservation_change、confirm_proposal。名称・スキーマは契約設計Taskで確定する。
- 出力ポートは予約・提案Repositoryと時刻取得を抽象化する。インメモリアダプターはRestaurantプロセスだけが所有し、再起動で架空の初期データに戻す。
- 空席再確認・提案の消費・予約の登録または置換を一体の処理にする。変更失敗時は元の予約を維持する。同じ予約に対する古い変更提案や二重承認による誤更新を防ぐ。
- Front Deskは公開A2A経由でRestaurantに依頼し、内部toolやRepositoryを直接呼ばない。店舗固有の判断はRestaurantに置く。
- tool化とRestaurantへのLLM追加は別の判断であり、LLM追加は未決とする。

### 模擬店舗の業務ルール

| 項目 | 決定 |
|---|---|
| 対象 | 館内1店舗、新規予約と既存予約の変更 |
| 営業時間 | ランチ11:00〜15:00、ディナー17:00〜22:00 |
| 予約開始・利用時間 | 30分刻み、90分。最終開始は13:30／20:30 |
| 予約可能日 | ホテル現地日付の当日から30日先まで。過去時刻は不可 |
| 通常テーブル | 2名卓×2、4名卓×2、6名卓×1 |
| 個室 | 6名用×1、2〜6名で利用可能、追加料金なし |
| 席の割り当て | 指定席種で人数を収容できる最小の空き卓。全員を1卓に案内し卓は結合しない |
| 人数 | 年齢を問わず1人1席 |
| 席の希望 | 通常テーブル／個室は確約。窓際は希望として受付け、確約しない |
| 代替候補 | 同じ営業枠、希望時刻の前後60分以内、近い順に最大3候補 |
| 条件を緩める相談 | 指定席種の候補を先に提示する。席種変更の検索や時間範囲拡大は確認してから行う |
| 仮押さえ | 行わない。承認時に再確認し、満席なら確定せず再提案する |

これらは実ホテル共通の規則ではなく、合意したデモ店舗の設定である。

### 会話・照合・承認

- 日付・時刻・人数・席種の不足項目をまとめて確認する。「席種の希望なし」が明示された場合は通常テーブルとする。情報不足を勝手に補完しない。
- 既存予約は架空の部屋番号と氏名の両方で照合し、複数ある場合は日時を確認して選ぶ。日時でも区別できなければ予約IDなどで選択し、推測で更新しない。
- 新規予約の所有者情報・会話と提案の結び付け方は契約設計Taskで確定する。
- 確定前に日付・時刻・人数・席種・90分利用・確約できない希望を提示し、ゲストの明示承認を得る。
- 検索と提案には確定の副作用を持たせない。拒否・曖昧な回答で確定しない。承認は対象提案に結び付け、LLMが承認済みフラグを生成しただけでは確定できない境界を設計する。

## 理由

- 実装詳細から業務ルールを独立させることで、toolや保存先の変更時にも予約判断を再利用できる。
- インメモリ保存はローカルデモに十分で、外部DBや予約システムの導入を必要としない。
- 提案と確定の分離により、条件相談を維持しながら未承認の変更と二重予約を防ぐ。

## 検討した代替案

- Agent内に業務・保存処理を集約する: 境界が曖昧になり、拡張時の影響が大きいため採用しない。
- 独立したREST APIサーバーを先に導入する: 現段階では別サービスの運用は不要。入力アダプター追加で将来対応する。
- DB保存: 永続化は今回不要。Repositoryポート越しに将来置換できるようにする。
- 提案時に仮押さえする: 有効期限や解除処理が増えるため採用しない。
- Restaurantに直ちにLLMを追加する: 合意されていないため先回りして確定しない。

## 影響・セキュリティ・運用

- Restaurantの固定予約契約とFront Deskの限定的な意図抽出・承認表示は拡張が必要。既存代表シナリオの移行方針を契約設計時に記録する。
- 部屋番号と氏名の照合はデモ用検索であり、本番の本人認証・認可を保証しない。照合失敗時に他ゲストの候補を公開しない。
- 架空データのみを使い、氏名・部屋番号を通常ログや通信デバッグ表示へ不要に露出しない。
- 予約・提案は再起動で失われ、複数プロセス間では共有されない。Restaurantの状態を持つプロセスは単一とし、水平分散を対象にしない。
- 提案IDの他会話からの利用、再利用、古い変更提案を検証し、同一卓の同時確定でも重複予約を作らない。
- MaintenanceとHousekeepingの業務拡充は対象外。予約取消、卓結合、食事制限、ルームサービス、料金・決済、外部システム連携も対象外。

## 実装前に解決する未決事項

- RestaurantにLLMを追加するか、構造化入力を固定ロジックで処理するか。追加する場合は別ADRで承認を記録する。
- ホテルのタイムゾーン、曖昧な日時の扱い、同距離候補・同定員卓の選択順。
- 新規予約の所有者情報、予約ID、提案IDの会話への紐付け、提案期限・破棄・再送時の応答、変更対象の競合検出。
- 入出力スキーマ、既存契約の移行、UIと会話状態の扱い。

これらを先頭の設計Taskで解決し、影響する実装を先行させない。
